## Conductor Research (2026-02-05)

### Confirmed from Conductor docs

1. Workflow and PR lifecycle
- Conductor explicitly frames the workflow as: develop -> review/test -> create PR + merge -> archive.
- The docs call out `Create PR (⌘⇧P)` and state Conductor helps fix failed checks before merge.
- Source: https://docs.conductor.build/workflow

2. Review UX
- Diff Viewer is the central review step and is positioned as the path to merge.
- Source: https://docs.conductor.build/core/diff-viewer

3. Merge gating
- Todos are merge gates: workspaces are blocked until todos are checked off.
- Source: https://docs.conductor.build/core/todos

4. Chat-driven operations
- Slash commands are chat-native and backed by markdown files (`~/.claude/commands/*.md`).
- Checkpoints are turn-based and can revert both conversation and code changes after a selected turn.
- Archived workspaces retain chat history and can be restored later.
- Source: https://docs.conductor.build/core/slash-commands
- Source: https://docs.conductor.build/core/checkpoints
- Source: https://docs.conductor.build/workflow

5. Workspace/branch behavior
- Each workspace maps to isolated copy + branch.
- On first chat, Conductor instructs the agent to rename the branch to match current work.
- Source: https://docs.conductor.build/first-workspace
- Source: https://docs.conductor.build/tips/workspaces-and-branches

6. PR actions via agent prompting
- Conductor says it injects system prompts for UI actions, including clicking `Create PR`.
- Source: https://docs.conductor.build/faq

7. Security model note
- Docs state agents run with user-level permissions and without sandboxing.
- This is an explicit product tradeoff vs agency's sandbox-first model.
- Source: https://docs.conductor.build/faq

### Parity Scope Proposal for agency

1. v2.1 parity minimum (CLI/TUI-first)
- `watch` replacement must show an invocation-centric "checks" surface:
- status, landing eligibility, failing checks, pending todos, PR state summary.
- add explicit `agent pr create`, `agent pr status`, `agent merge` flows (or equivalent names) with deterministic output and `--json`.

2. Chat parity baseline (headless)
- add read/write chat control plane for headless invocations:
- stream transcript, send follow-up prompt, restart runner in-place, resume from checkpoint.
- expose this first via CLI (`agent chat`, `agent logs --follow`, `agent restart`) before full TUI.

3. Review parity baseline
- provide invocation diff surfaces tied to conversation turns/checkpoints (turn-to-diff mapping).
- make review actions explicit: `request-review` (AI/self-review), `accept`, `needs-fix`.

4. Merge gating parity baseline
- gate merge on:
- clean git state in sandbox/integration as applicable
- checks pass policy
- todo completion policy
- optional required human review policy

5. Non-goal for v2.1
- do not match Conductor's unsandboxed trust model; keep sandbox isolation as invariant.

## PR/Review/Merge SOTA Scan (2026-02-05)

### Competitive landscape (what mature teams are using now)

1. GitHub native (baseline most teams converge on)
- Required PR path + approval/review rules + CODEOWNERS + stale-review handling + "last pusher must not self-approve" style constraints.
- Merge queue with `merge_group` CI orchestration, concurrency controls, queue grouping, and CI timeout/merge limits.
- Auto-merge + review re-request + apply suggestion batches in one commit.
- AI review is additive, not authoritative: Copilot leaves comment-only reviews and does not satisfy required approvals.
- Sources:
  - https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets
  - https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/merging-a-pull-request-with-a-merge-queue
  - https://docs.github.com/en/enterprise-server%403.17/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue
  - https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/reviewing-proposed-changes-in-a-pull-request
  - https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/incorporating-feedback-in-your-pull-request
  - https://docs.github.com/en/copilot/concepts/agents/code-review
  - https://docs.github.com/en/copilot/how-tos/use-copilot-agents/request-a-code-review/use-code-review

2. Graphite (stacked workflow + PR-native AI collaboration)
- Stack-aware merge queue with explicit positioning against sequential queues.
- PR review UI with timeline/file-tree/focus mode and stack navigation.
- Chat-in-review model: ask for summary, review guidance, CI debugging, and apply edits directly in PR.
- Sources:
  - https://graphite.com/docs/graphite-merge-queue
  - https://graphite.com/docs/review-pull-requests
  - https://graphite.com/docs/graphite-chat

3. GitLab (merge trains + strong approval policy model)
- Merge trains + merged-results pipelines validate combined future state and run train pipelines in parallel.
- Explicit failure handling: drop failing MR, recompute downstream train pipelines.
- Approval system supports required approvals, reviewer status, Code Owners, and merge blocks from open threads/failed pipeline.
- Sources:
  - https://docs.gitlab.com/ci/pipelines/merge_trains/
  - https://docs.gitlab.com/ci/pipelines/merged_results_pipelines/
  - https://docs.gitlab.com/user/project/merge_requests/approvals/

4. Mergify / queue specialists (CI-cost optimization and throughput)
- Batch queueing (`batch_size`) + automatic culprit isolation when a batch fails.
- Optional "merge what was tested" fast-forward mode for stronger SHA traceability.
- Sources:
  - https://docs.mergify.com/merge-queue/batches/
  - https://docs.mergify.com/merge-queue/rules/

5. Reviewable / policy layers (highly customizable completion logic)
- Review completeness can be script-defined (custom completion condition), beyond host platform defaults.
- Review state often combines: mergeability + file-reviewed state + discussion resolution + CI panel.
- Sources:
  - https://docs.reviewable.io/reviews.html
  - https://docs.reviewable.io/repositories.html

6. Stacked diff ecosystem (Sapling/ReviewStack/ghstack lineage)
- Strong theme: split large changes into independently reviewable layers.
- ReviewStack explicitly optimizes for independent review of each stack element.
- Tradeoff remains: many stacked workflows look awkward in vanilla GitHub UI and need specialized review surfaces.
- Sources:
  - https://sapling-scm.com/docs/addons/reviewstack/
  - https://sapling-scm.com/docs/git/sapling-stack/
  - https://github.com/ezyang/ghstack

### SOTA patterns (cross-tool convergence)

1. Merge-time reliability is queue-driven, not human-rebase-driven
- Teams are moving from "please rebase and rerun manually" to queue+grouped-CI orchestration.

2. Review policy is explicit and machine-enforced
- Approval requirements, code owner routing, unresolved-thread gating, and status-check contracts are first-class.

3. AI is reviewer acceleration, not merge authority
- AI comments are high-signal assistants; human approval remains canonical in mature governance setups.

4. Incremental review beats monolithic review
- Stacked diffs and delta-only re-reviews reduce reviewer fatigue and cycle time.

5. In-review remediation is expected
- Best-in-class UX allows fixing issues directly from review context (apply suggestions, chat->edit, rerun checks).

### How engineers tend to prefer reviewing agent changes

Inference from feature convergence above:

1. They want "prove it" review surfaces, not opaque agent claims
- clear diff per logical change
- exact failing/passing checks
- explicit unresolved comments/todos
- reproducible test evidence attached to the change

2. They want small, independently reviewable units
- stacked changes or scoped commits
- ability to approve lower layers while higher layers keep evolving

3. They want AI to triage, summarize, and propose fixes, but not to silently self-approve
- comment-only AI reviews fit current trust model better than binding AI approvals

4. They want merge safety mostly automated
- queue + required checks + policy gates
- minimal manual rebase choreography

### What teams often wish they had (or had better)

1. Turn-to-diff traceability for agent sessions
- "show exactly what changed for prompt/turn N"

2. Confidence scoring and policy-aware AI review
- "which comments are likely real issues vs noise"
- "which comments are blocking by policy vs advisory"

3. Better review ergonomics for large AI-authored diffs
- automatic semantic chunking by subsystem/risk
- dependency-aware review ordering

4. Fast local pre-PR review loops
- cheap uncommitted-change review before opening PR to reduce PR noise

### Implications for agency v2.1 scope

1. `watch` should prioritize a checks-first review/merge control plane
- queue status (or equivalent), required checks, approval gates, unresolved threads/todos

2. Agent chat parity should include review-context actions
- ask for diff summary, request targeted fix, apply patch, rerun checks from the same surface

3. Keep human approval as non-negotiable
- AI review should be advisory and auditable

4. Add stack-friendly review primitives early
- invocation-to-branch mapping, per-invocation diff isolation, "review next change" navigation

## Differentiator Clarifications

### 1) Local-first deterministic daemon/state model

What it is:
- "Local-first": source of truth lives on the developer machine (store + git + local daemon), not a remote orchestration service.
- "Deterministic": mutation operations have one authoritative writer path and idempotent semantics where possible.

What we already have:
- daemon-owned mutation path for v2 worktree create (`internal/commands/worktree.go:38`).
- daemon-owned mutation path for v2 agent starts (`internal/commands/agent.go:64`).
- worktree create uses idempotency key (`internal/commands/worktree.go:79`).

Why we do not fully have it yet:
- v1 legacy flows still coexist and mutate state outside the new control plane.
- some v2 commands still resolve from local store directly instead of daemon read API (`internal/commands/agent.go:1016`, `internal/commands/agent.go:542`).
- `watch` (intended central read surface) is not implemented yet (`internal/cli/cobra/watch.go:25`).

### 2) Runner-portable model with consistent CLI + JSON outputs

What it is:
- "Runner-portable": add/swap runners without changing core invocation semantics.
- "Consistent CLI + JSON": each important operation has stable human output and machine-parsable output for automation.

What we already have:
- runner command resolution supports configured runner names in principle (`internal/config/runner.go:15`).
- daemon read API plus `--json` output exists for key list/show/checkpoint commands (`internal/commands/agent.go:339`, `internal/commands/worktree.go:193`, `internal/cli/cobra/checkpoint.go:80`).
- normalized stream schema concept exists across runners (`README.md:322`).

Why we do not fully have it yet:
- agent start paths hard-allow only `claude|codex` (`internal/commands/agent.go:85`, `internal/daemon/handlers.go:1514`).
- stream adapters only exist for those two runners (`internal/daemon/stream/adapter.go:30`).
- many mutation commands still do not support `--json` output (for example `agent start`, `agent open`, `agent stop`, `agent kill` in `internal/cli/cobra/agent.go`).

### 3) Strong checkpoint/rollback tied to sandbox state

What it is:
- checkpoints snapshot sandbox content over time and rollback restores that exact sandbox working state, without polluting integration branches.
- "Tied to sandbox state" means checkpoint lifecycle is invocation-scoped and path-scoped.

What we already have:
- daemon checkpoint engine per sandbox with fsnotify + polling, dedupe, rate limit, and final checkpoint (`internal/daemon/checkpoint/engine.go:21`, `internal/daemon/checkpoint/engine.go:73`, `internal/daemon/checkpoint/engine.go:246`).
- checkpoint apply endpoint validates invocation state and restores sandbox (`internal/daemon/checkpoint_handlers.go:79`, `internal/daemon/checkpoint_handlers.go:103`).
- CLI supports `checkpoint ls` and `checkpoint apply` (`internal/cli/cobra/checkpoint.go:26`).

Why we do not fully have it yet:
- checkpoint apply is limited to headless invocations (`internal/daemon/checkpoint_handlers.go:72`).
- no "restart from checkpoint" or conversational resume flow integrated with `agent` commands yet.
- no watch/TUI checkpoint UX yet, so rollback remains CLI-only.
