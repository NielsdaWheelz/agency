# pr-01: daemon read api contract hardening

Last updated: 2026-02-25
Status: draft
Upstream l2: `docs/v2.1/s2/s2_spec.md`
Upstream l3: `docs/v2.1/s2/s2_roadmap.md` (PR-01)

## goal
Align S2 daemon read endpoints used by `agent`/`worktree` list/show flows to the L2 read contract with deterministic envelopes, strict enum filter validation, and stable pagination/filter behavior.

## deliverables

### `internal/daemon/read_types.go`
- add a structured details type for invalid list-filter enum inputs matching L2 `InvalidQueryArgumentDetails`:
  - `param`
  - `value`
  - `allowed_values`
- use JSON field names exactly as the L2 contract (`param`, `value`, `allowed_values`).
- do not change the daemon read response envelope field names or omit/add envelope fields in this PR.
- do not add new public error codes in this file or elsewhere for PR-01.

### `internal/daemon/read_handlers.go`
- harden `GET /worktrees` and `GET /invocations` list handlers to validate enum query params before repo scan/filter evaluation:
  - `/worktrees`: `state` in `present|archived|all`
  - `/invocations`: `state` in `active|finished|all`
  - `/invocations`: `mode` in `headed|headless|all`
- on invalid enum input, return:
  - HTTP `400`
  - `error_code = E_INVALID_ARGUMENT`
  - structured `details` with `param`, `value`, `allowed_values`
  - no repo enumeration or local scan work performed after validation failure
- preserve existing deterministic unresolved-`worktree_ref` behavior for invocation lists:
  - unresolved `worktree_ref` returns an empty list
  - request must not silently widen to an unfiltered list
- preserve current daemon compatibility support for `worktree_id` on `GET /invocations` as a non-normative input:
  - `worktree_ref` remains the only S2-documented canonical filter parameter
  - when both `worktree_ref` and `worktree_id` are provided, `worktree_ref` takes precedence deterministically
  - compatibility behavior must not silently widen results
- preserve existing show endpoint semantics and list endpoint envelope shape for:
  - `GET /worktrees`
  - `GET /worktrees/{ref}`
  - `GET /invocations`
  - `GET /invocations/{ref}`
- preserve pagination behavior for list endpoints:
  - default `limit=100`
  - accepted max `limit=500`
  - opaque cursor continuity remains exclusive and deterministic
- do not add CLI routing, daemon bootstrap logic changes, or navigation-kernel behavior (PR-02+).

### `internal/daemon/read_handlers_test.go`
- add/upgrade handler tests for strict invalid enum rejection on list endpoints with structured error details:
  - invalid `/worktrees?state=...`
  - invalid `/invocations?state=...`
  - invalid `/invocations?mode=...`
  - combined invalid invocation filters should return one deterministic invalid-argument error (see decision ledger)
  - invalid enum requests fail before repo-index enumeration/scan work (no `E_INTERNAL` fallback when repo lookup would otherwise fail)
- assert invalid-filter requests fail closed:
  - status `400`
  - `error_code == E_INVALID_ARGUMENT`
  - `details.param`, `details.value`, `details.allowed_values` are present and correct
  - no widened success response path
- retain and, where needed, tighten existing regression tests for:
  - `worktree_ref` unresolved => empty list (not widened)
  - `worktree_id` compatibility filtering remains deterministic
  - `worktree_ref` vs `worktree_id` precedence remains deterministic (`worktree_ref` wins)
  - ambiguous `GET /worktrees/{ref}` and `GET /invocations/{ref}` responses preserve `409` semantics and candidate details when available
  - list pagination cursor continuation for worktrees/invocations
  - envelope presence on success/error responses
- add endpoint-level regression coverage that `limit=500` remains accepted on list endpoints (without introducing new `limit` rejection semantics).

## decision ledger

| question | decision | rationale | fallback/default |
|---|---|---|---|
| Where should `state`/`mode` strict validation run? | Validate at list-handler boundary before repo enumeration and filtering. | Fail-fast preserves capacity at fleet scale and guarantees no silent widening from matcher defaults. | none |
| Does PR-01 tighten `limit` or `cursor` invalid-input semantics beyond L2/L3? | No. PR-01 preserves current `limit`/cursor handling and only hardens `state`/`mode` strictness. | L2/L3 explicitly require strict enum validation; expanding parameter semantics here creates scope smuggling into an unplanned contract change. | Preserve current behavior and document if future hardening is needed. |
| How is structured invalid-filter error detail shaped? | JSON object with exact fields `param`, `value`, `allowed_values`. | Matches L2 `InvalidQueryArgumentDetails` and supports machine-safe CLI/script handling. | none |
| How should PR-01 handle existing undocumented `worktree_id` on `GET /invocations` while S2 canonically documents `worktree_ref`? | Preserve `worktree_id` as compatibility-only behavior in PR-01; keep `worktree_ref` canonical and lock deterministic precedence (`worktree_ref` over `worktree_id`) with tests. | Avoids breaking unknown daemon clients during a hardening PR while preventing canonical API-surface drift and ambiguity. | If compatibility removal is later desired, stage it in an explicitly owned compatibility/API cleanup PR with deprecation policy. |
| When both `state` and `mode` are invalid on `GET /invocations`, which invalid param is returned? | Validate in deterministic order `state` then `mode`; first invalid wins and returns the single `E_INVALID_ARGUMENT` response. | Preserves L2 singular detail shape while making behavior deterministic and script-safe. | If multi-error reporting is needed later, introduce a versioned/expanded details schema in a dedicated contract change. |
