### `internal/releasegates/types.go`
- add long-lived release-gating DTOs that are not slice-temporary package names:
  - `ReleaseReadinessRequest`
  - `ReleaseReadinessResult`
  - `ClosureReportRequest`
  - `ClosureReportResult`
  - `GateClosureSnapshot`
  - `ClosedItemEvidence`
  - `FreezeReadinessRequest`
  - `FreezeReadinessResult`
- encode deterministic field names and ordering expectations for downstream daemon/client/report consumers.
- define canonical source constants used by PR-05 orchestration (`docs/v2.1/constitution.md`, `docs/v2.1/s1/s1_spec.md`).

### `internal/releasegates/service.go`
- implement PR-05 orchestration service that consumes PR-03/PR-04 outputs without redefining them:
  - `EvaluateReleaseReadiness(req ReleaseReadinessRequest, repoRoot string) (*ReleaseReadinessResult, error)`
  - `BuildClosureReport(req ClosureReportRequest, repoRoot string) (*ClosureReportResult, error)`
  - `EvaluateFreezeReadiness(req FreezeReadinessRequest, repoRoot string) (*FreezeReadinessResult, error)`
- release-readiness behavior:
  - use migrated `internal/releasegates.RequireSliceReady` with parity to PR-03 semantics as the binding readiness primitive.
  - preserve PR-03 error semantics/details for `E_GATE_BLOCKED` and `E_GATE_SET_*`.
  - do not introduce ad-hoc readiness heuristics.
- closure-report behavior:
  - consume canonical gate ordering from PR-03 gate set evaluation.
  - include closure evidence for closed+valid items only (`state=closed` and no `blocking_code`).
  - include deterministic gate-level totals, closed counts, blocking items, and closure evidence payloads.
  - deterministic ordering: Gate A source order, then Gate B source order, with stable key set.
- freeze-readiness behavior:
  - parse unresolved-default rows from `docs/v2.1/s1/s1_spec.md` Section 9 table.
  - return `freeze_ready=true` iff unresolved row count is `0`.
  - unresolved rows block freeze with `E_GATE_BLOCKED`; detail keys fixed:
    - `freeze_ready`
    - `unresolved_count`
    - `spec_path`
    - `first_question`
  - malformed/unreadable spec source returns `E_GATE_SET_INVALID` with deterministic detail key `spec_path`.

## decision ledger

| question | decision | rationale | fallback/default |
|---|---|---|---|
| Where should PR-05 release enforcement live operationally? | Daemon-first read endpoints plus daemonclient/command consumers. | Keeps release-read/write authority centralized in daemon, consistent with v2.1 architecture. | If CLI must run without daemon, no local fallback is added in PR-05; daemon availability remains required. |
| How should blocked release readiness be surfaced? | Use PR-03 `RequireSliceReady` semantics and propagate `E_GATE_BLOCKED` unchanged. | Prevents ad-hoc reinterpretation and preserves prior deterministic details contract. | Any future change must update PR-03 + PR-05 specs and tests in the same change set. |
| How should closure reporting avoid drift from policy primitives? | Build reports from canonical gate ordering + parsed closure evidence from existing evaluators/parsers only. | Guarantees one source of truth and deterministic report output for automation/audit. | If evidence parsing fails for a closed item, report call fails with deterministic error instead of silently omitting. |
| How should freeze-readiness be determined? | Parse Section 9 unresolved-default rows in `docs/v2.1/s1/s1_spec.md`; unresolved count > 0 blocks freeze. | Directly encodes L2 invariant 11 and acceptance scenario without introducing side metadata files. | If source cannot be parsed/read, return `E_GATE_SET_INVALID` with `spec_path`. |
| How should `internal/s1gates` cruft be handled? | Hard-delete `internal/s1gates` in PR-05 after full migration to `internal/releasegates` with behavior parity. | Keeps codebase clean before S2 and eliminates temporary slice-scoped namespace debt. | No fallback: PR-05 remains incomplete until `internal/s1gates` is fully removed. |
| Should PR-05 add new error-code families? | No new error families; reuse `E_GATE_BLOCKED` and existing S1 gate errors with fixed detail schemas. | Minimizes contract churn and keeps S1 error model stable for downstream tools. | If future governance needs separate code, update L2 error model first, then downstream layers. |
| How should issue artifacts evolve after S1? | GitHub issues are the long-term canonical issue source; markdown issue stubs are S1 compatibility inputs only. | Aligns release governance with enterprise workflow and removes local-doc issue coupling over time. | Until GH provider lands, `MarkdownIssueSource` is the only enabled provider behind the interface. |
