### `internal/s1gates/change_validate.go`
- implement `ValidateGateSetChange(req GateSetChange, repoRoot string) (*GateSetChangeValidationResult, error)`.
- deterministic validation precedence:
  1. `reason` validation (`E_GATE_CHANGE_REASON_REQUIRED`)
  2. `gate_id`/`change_type`/target-shape validation (`E_GATE_CHANGE_TARGET_REQUIRED`)
  3. approval validation (`E_GATE_CHANGE_APPROVAL_REQUIRED`)
  4. synchronization validation (`E_GATE_SET_DRIFT`)
  5. success (`{valid: true}`)
- request validation:
  - require non-empty `reason`; missing/empty => `E_GATE_CHANGE_REASON_REQUIRED`.
  - require strict case-sensitive enum values:
    - `gate_id` must be exactly `A` or `B`
    - `change_type` must be exactly `add`, `remove`, `replace`, or `reorder`
  - invalid enum values (including case-variant values) => `E_GATE_CHANGE_TARGET_REQUIRED` with `target_violation=invalid_enum`.
  - enforce target-field requirements by change type:
    - `add`, `remove` require non-empty `issue_path`
    - `replace` requires `issue_paths` length `== 2`
    - `reorder` requires `issue_paths` length `>= 2`
  - enforce target-field exclusivity by change type:
    - `add`, `remove` reject non-empty `issue_paths`
    - `replace`, `reorder` reject non-empty `issue_path`
  - missing/invalid target requirements => `E_GATE_CHANGE_TARGET_REQUIRED`.
- membership intent policy for `issue_path` operations:
  - `add`: `issue_path` must resolve to an existing issue stub and must not already be a member of Gate A or Gate B.
  - `remove`: `issue_path` must already be a member of the targeted gate.
  - membership-intent violations => `E_GATE_CHANGE_TARGET_REQUIRED` with `target_violation=membership_intent`.
- replace policy:
  - `replace` uses `issue_paths=[from_issue_path, to_issue_path]`.
  - `from_issue_path` must be a current member of the targeted gate.
  - `to_issue_path` must resolve to an existing issue stub and must not already be a member of Gate A or Gate B.
  - `from_issue_path` and `to_issue_path` must be different paths.
  - replace violations => `E_GATE_CHANGE_TARGET_REQUIRED` with `target_violation=membership_intent`.
- reorder policy:
  - `reorder` is permutation-only over existing membership of the targeted gate (`gate_id`).
  - membership-changing `reorder` proposals (missing member, extra member, duplicate member, or cross-gate member) are invalid even when `approved_by` is present.
  - membership-changing reorder => `E_GATE_CHANGE_TARGET_REQUIRED` with `target_violation=membership_reorder`.
- approval policy:
  - `remove` and `replace` require non-empty `approved_by`; missing => `E_GATE_CHANGE_APPROVAL_REQUIRED`.
  - `add` and `reorder` do not require `approved_by`.
- synchronization policy:
  - `synced_issue_map` must be `true`; `false` => `E_GATE_SET_DRIFT`.
  - validator must parse canonical `release-gates.md` and `issue-map.md` and verify no gate-membership drift at evaluation time.
  - parser implementation strategy must not create a hard dependency on PR-03 ownership surfaces; reuse of merged PR-03 parser is allowed but optional.
  - drift semantics match S1 canonical rule: each Gate A/B issue path appears exactly once in `issue-map.md`.
  - drift/mismatch => `E_GATE_SET_DRIFT`.
  - source read/parse failures for canonical sync inputs are normalized to `E_GATE_SET_DRIFT` with `drift_kind=source_invalid`.
- error detail schema is fixed for all change-validation errors:
  - `E_GATE_CHANGE_REASON_REQUIRED`:
    - `gate_id`
    - `change_type`
    - `field` (`reason`)
  - `E_GATE_CHANGE_TARGET_REQUIRED`:
    - `gate_id`
    - `change_type`
    - `target_kind` (`issue_path` or `issue_paths`)
    - `target_violation` (`missing`, `invalid_enum`, `exclusivity`, `membership_intent`, or `membership_reorder`)
  - `E_GATE_CHANGE_APPROVAL_REQUIRED`:
    - `gate_id`
    - `change_type`
    - `field` (`approved_by`)
  - `E_GATE_SET_DRIFT`:
    - `issue_path`
    - `issue_map_count`
    - `drift_kind` (`missing`, `duplicate`, `unsynced_flag`, or `source_invalid`)
    - `sync_source` (`release-gates_vs_issue-map`)
    - for `drift_kind=unsynced_flag`, set `issue_path=""` and `issue_map_count=""` (keys remain present).
    - for `drift_kind=source_invalid`, set `issue_path=""` and `issue_map_count=""` (keys remain present).
- on success return `{valid: true}` with no side effects (validation-only, no mutation).

## decision ledger

| question | decision | rationale | fallback/default |
|---|---|---|---|
| Should `synced_issue_map` be treated as caller declaration only, or verified against canonical docs? | Dual validation: require `synced_issue_map=true` and independently verify canonical `release-gates.md` vs `issue-map.md` synchronization at validation time. | Prevents false approvals when caller sets `synced_issue_map=true` despite actual drift; improves audit and release safety. | Any sync failure returns `E_GATE_SET_DRIFT` with deterministic detail keys. |
| Should `change_type=reorder` allow membership changes when an approver is present? | No. `reorder` is strictly membership-preserving (permutation-only) for the targeted gate. | Prevents mutation-class ambiguity and policy bypass; keeps `add/remove/replace` as the only membership-changing operations. | Membership-changing reorder returns `E_GATE_CHANGE_TARGET_REQUIRED` regardless of `approved_by`. |
| How should one error be selected when multiple change-validation checks fail in a single request? | Apply fixed precedence: reason -> target-shape -> approval -> synchronization. | Keeps API deterministic for CI/automation and avoids incidental first-failure variance. | Any precedence change requires same-PR spec + tests update. |
| How should `replace` target semantics be validated? | `replace` requires `issue_paths=[from,to]` where `from` is current targeted-gate member and `to` is existing global non-member. | Removes ambiguity and makes replace behavior machine-checkable without out-of-band interpretation. | Invalid replace pair semantics return `E_GATE_CHANGE_TARGET_REQUIRED`. |
| Should change requests allow both `issue_path` and `issue_paths` simultaneously? | No. Enforce strict target-field exclusivity by `change_type`. | Eliminates ambiguous mutation intent and prevents implicit precedence between conflicting target fields. | Any exclusivity violation returns `E_GATE_CHANGE_TARGET_REQUIRED`. |
| Should `add` allow inserting an issue already present in the other gate? | No. `add` requires global non-membership across Gate A and Gate B. | Prevents cross-gate duplicates and keeps gate membership globally deterministic. | If already present in either gate, return `E_GATE_CHANGE_TARGET_REQUIRED`. |
| Should PR-04 standardize detail-key schemas for all change-validation errors? | Yes. Fix deterministic detail keys for `E_GATE_CHANGE_REASON_REQUIRED`, `E_GATE_CHANGE_TARGET_REQUIRED`, `E_GATE_CHANGE_APPROVAL_REQUIRED`, and `E_GATE_SET_DRIFT`. | Enables stable machine parsing in CLI/CI/reporting and prevents drift from free-form error payloads. | Any schema change requires same-PR spec + tests updates. |
| Should `E_GATE_SET_DRIFT` allow missing `issue_path`/`issue_map_count` keys for `unsynced_flag`? | No. Keep all drift detail keys always present; use empty-string values for non-applicable fields in `unsynced_flag`. | Preserves deterministic schema shape and avoids conditional key parsing in automation. | `unsynced_flag` sets `issue_path=""` and `issue_map_count=""`. |
| How should `change-validate` report canonical source read/parse failures during synchronization checks? | Normalize to `E_GATE_SET_DRIFT` with `drift_kind=source_invalid`. | Keeps change-validate error surface stable and avoids mid-PR contract widening. | Use empty-string normalization for `issue_path` and `issue_map_count`. |
| Should `gate_id` and `change_type` enum parsing allow case normalization (for example `a`, `Add`, `REORDER`)? | No. Enforce strict case-sensitive exact enum matching. | Avoids hidden coercion semantics and keeps request contracts deterministic across clients and languages. | Any case-variant or unknown enum value returns `E_GATE_CHANGE_TARGET_REQUIRED` with `target_violation=invalid_enum`. |
| How should PR-04 handle availability of PR-03 issue-map parser while L3 keeps PR-04 dependency at PR-01? | Treat PR-03 parser reuse as optional merged-state reuse, not a required dependency. | Preserves L3 dependency contract and keeps PR-04 independently implementable and merge-safe. | If PR-03 parser reuse is unavailable, PR-04 uses local equivalent sync parsing logic. |

## acceptance tests

### file: `internal/s1gates/change_validate_test.go`

**test: `TestValidateGateSetChange_ReasonRequired`**
- input: change-validate requests with empty/missing `reason` across supported `change_type` values.
- output: returns `E_GATE_CHANGE_REASON_REQUIRED`.

**test: `TestValidateGateSetChange_TargetRequiredByChangeType`**
- input:
  1. `add/remove` requests missing `issue_path`
  2. `replace` requests missing `issue_paths` or with length `!= 2`
  3. `reorder` request with `issue_paths` length `< 2`.
- output: each returns `E_GATE_CHANGE_TARGET_REQUIRED`.

**test: `TestValidateGateSetChange_TargetFieldExclusivityRules`**
- input:
  1. `add/remove` requests with non-empty `issue_paths`
  2. `replace/reorder` requests with non-empty `issue_path`.
- output: each returns `E_GATE_CHANGE_TARGET_REQUIRED`.

**test: `TestValidateGateSetChange_IssuePathMembershipIntentRules`**
- input:
  1. `add` request where `issue_path` already belongs to targeted gate
  2. `add` request where `issue_path` already belongs to the other gate
  3. `add` request where `issue_path` does not exist
  4. `remove` request where `issue_path` is not in targeted gate.
- output: each returns `E_GATE_CHANGE_TARGET_REQUIRED`.

**test: `TestValidateGateSetChange_ReplaceTargetRules`**
- input:
  1. `replace` request where `from_issue_path` is not in targeted gate
  2. `replace` request where `to_issue_path` already belongs to Gate A or Gate B
  3. `replace` request where `to_issue_path` does not exist
  4. `replace` request where `from_issue_path == to_issue_path`.
- output: each returns `E_GATE_CHANGE_TARGET_REQUIRED`.

**test: `TestValidateGateSetChange_InvalidEnumValuesReturnTargetRequired`**
- input: requests with invalid or case-variant enum values for `gate_id`/`change_type` (for example `a`, `b`, `Add`, `REORDER`).
- output: returns `E_GATE_CHANGE_TARGET_REQUIRED`.

**test: `TestValidateGateSetChange_RemoveRequiresApproval`**
- input: valid `remove` request with empty `approved_by`.
- output: returns `E_GATE_CHANGE_APPROVAL_REQUIRED`.

**test: `TestValidateGateSetChange_ReplaceRequiresApproval`**
- input: valid `replace` request (`issue_paths=[from,to]`) with empty `approved_by`.
- output: returns `E_GATE_CHANGE_APPROVAL_REQUIRED`.

**test: `TestValidateGateSetChange_ReorderMembershipRules`**
- input: `reorder` requests over canonical Gate A/B membership with both membership-preserving and membership-changing `issue_paths`.
- output:
  - membership-preserving permutation succeeds when other guards pass.
  - membership-changing reorder returns `E_GATE_CHANGE_TARGET_REQUIRED` even when `approved_by` is non-empty.

**test: `TestValidateGateSetChange_SyncedFlagFalseReturnsDrift`**
- input: otherwise valid request with `synced_issue_map=false`.
- output:
  - returns `E_GATE_SET_DRIFT`
  - details include full fixed drift key set
  - `drift_kind=unsynced_flag`, `sync_source=release-gates_vs_issue-map`, `issue_path=""`, and `issue_map_count=""`.

**test: `TestValidateGateSetChange_DetectsIssueMapDrift`**
- input: otherwise valid request over fixture with gate-item missing or duplicated in `issue-map.md`.
- output:
  - returns `E_GATE_SET_DRIFT`
  - details include deterministic mismatch keys (`issue_path`, `issue_map_count`, `drift_kind`, `sync_source`).

**test: `TestValidateGateSetChange_SourceInvalidReturnsDrift`**
- input: otherwise valid request over fixture with malformed or unreadable canonical `release-gates.md` or `issue-map.md`.
- output:
  - returns `E_GATE_SET_DRIFT`
  - details include `drift_kind=source_invalid`, `sync_source=release-gates_vs_issue-map`, `issue_path=""`, and `issue_map_count=""`.

**test: `TestValidateGateSetChange_SuccessWhenSynchronized`**
- input: valid request with all required fields, required approval (when applicable), `synced_issue_map=true`, and synchronized canonical docs.
- output:
  - succeeds
  - returns `{valid: true}`.

**test: `TestValidateGateSetChange_ErrorPrecedenceIsDeterministic`**
- input: requests intentionally failing multiple guards simultaneously.
- output: error code selection follows fixed precedence (`reason` -> `target` -> `approval` -> `drift`).

**test: `TestValidateGateSetChange_ErrorDetailSchemaIsDeterministic`**
- input: representative failing requests for `reason`, `target`, `approval`, and `drift` error paths.
- output:
  - each returned error contains the exact fixed detail-key set for its code
  - `target_violation` values are from the allowed enum set
  - `drift_kind` values are from the allowed enum set (`missing`, `duplicate`, `unsynced_flag`, `source_invalid`)
  - no free-form/unexpected detail keys are required for contract assertions.
