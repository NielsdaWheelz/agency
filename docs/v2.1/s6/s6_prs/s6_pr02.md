# PR-02: CLI Ergonomics Normalization for Confirmation, High-Traffic Flags, and Open-on-Create

## Goal

Standardize script-safe confirmation and high-frequency flag ergonomics across canonical and compatibility CLI paths without breaking existing command meaning.

## Builds On

PR-01 merged report contracts (and S5 invocation-centric progression baseline).

## Acceptance

- Destructive/irreversible flows (`agent merge`, `clean`, `resume --restart`, `worktree rm`, and explicitly-confirmed compatibility flows) share one non-interactive confirmation contract: without `--yes`, deterministic `E_CONFIRMATION_REQUIRED`; with `--yes`, deterministic non-interactive progression.
- Interactive confirmation-protected flows remain explicit and deterministic for humans, while `--yes` consistently bypasses prompt-only confirmation paths.
- High-traffic lifecycle/navigation/progression commands expose consistent canonical long flags with additive short aliases for repo selection, JSON output, confirmation, and open behavior: `-r/--repo`, `-j/--json`, `-y/--yes`, `-o/--open`.
- Alias rollout is compatibility-preserving: legacy spellings remain valid additive aliases and command meaning is unchanged.
- Open-on-create behavior is available for canonical creation and compatibility run/create flows, with deterministic outcomes in both interactive and scriptable contexts; when `--open` is set on flows that otherwise auto-attach, the flow is open-first and non-attach (detached-equivalent).
- Help output for covered commands reflects canonical long flags plus short aliases so human-facing docs and automation-facing behavior stay aligned.
- Automated coverage asserts the confirmation matrix (interactive/non-interactive, with/without `--yes`), alias parsing/behavior, and open-on-create behavior across canonical and compatibility command paths.
- Open-dispatch failures after successful creation are explicit and deterministic (human warning plus machine signal where supported) without retroactively failing or rolling back the creation operation.
- Existing machine-readable progression contracts remain stable after ergonomics normalization (no drift in deterministic JSON mutation/readiness behavior).

## Non-Goals

- No removal of legacy command paths or legacy flag spellings.
- No full command taxonomy rewrite or command-family redesign.
- No expansion beyond S6 ergonomics scope into report-contract redesign (owned by PR-01).
- No GUI/full-screen TUI workflow scope.

## Key Decisions (if any beyond L2)

**Confirmation error contract**: for confirmation-protected non-interactive paths, omission of `--yes` is treated as deterministic confirmation-required failure (not ad hoc interactive-terminal gating).

**Flag normalization boundary**: normalization targets high-traffic lifecycle/navigation/progression surfaces and remains additive; it is not a blanket rename/redefinition pass across every CLI command.

**Open-on-create interaction contract**: on creation flows that otherwise auto-attach, `--open` means create, then open, without implicit attach (detached-equivalent), so scripts and humans get one predictable post-create state.

**Open launch failure semantics**: if creation succeeds but editor launch fails, the command preserves successful creation and emits deterministic warning/signal output rather than converting the operation into a destructive or ambiguous failure.
