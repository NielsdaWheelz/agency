# PR-03: S6 Contract Closure for Alias Parity + Open-on-Create Guarantees

## Goal

Close remaining S6 ergonomics gaps so invocation progression/navigation alias behavior and open-on-create guarantees are fully spec-aligned and test asserted.

## Builds On

PR-02 merged.

## Acceptance

- Core invocation progression surfaces that already expose repo/json flags (including `agent review`) accept additive canonical short aliases (`-r/--repo`, `-j/--json`) without changing existing long-flag semantics or output contracts.
- High-traffic invocation navigation flows expose additive repo short-alias parity: canonical `agent path|open|attach|enter` and compatibility aliases `path|open|attach` accept `-r/--repo` without changing existing resolution behavior.
- `worktree create --open` and `run --open` preserve deterministic open-first behavior for creation flows that would otherwise auto-attach.
- When `--open` is requested and creation succeeds, editor-launch failure does not roll back creation and emits explicit deterministic `open_status: failed` signaling; successful launch emits deterministic `open_status: opened`.
- Covered command help output and parsing coverage assert visibility/availability of the new short aliases.
- Confirmation-protected non-interactive flows that require `--yes` retain deterministic confirmation-required behavior, with regression coverage preserved while adding the new alias/open assertions.

## Non-Goals

- No new command families or command-taxonomy redesign.
- No legacy alias removals or breaking flag renames.
- No reports-v2 contract redesign beyond PR-01 semantics.
- No expansion of merge/clean/restart confirmation semantics beyond regression protection.

## Key Decisions (if any beyond L2)

**Alias rollout boundary**: this closure pass is intentionally scoped to remaining high-traffic S6 gaps (progression repo/json parity plus canonical+compatibility navigation `-r` parity), not a blanket short-alias retrofit across every CLI command.

**Open failure semantics**: open dispatch remains post-create best-effort; creation success remains authoritative while `open_status` provides deterministic machine/human signaling for launch outcome.
