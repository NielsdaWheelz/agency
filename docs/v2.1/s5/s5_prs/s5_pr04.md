# PR-04: S5 Contract Closure + Failure-Path E2E Matrix

## Goal

Complete S5 contract and test closure so invocation-scoped review -> PR sync -> merge automation is deterministic, traceable, and CI-gated across happy and failure paths.

## Builds On

PR-03 merged.

## Acceptance

- The daemon API contract explicitly defines invocation-scoped review, PR sync, and merge endpoints with required request fields, success fields, and deterministic error envelope semantics.
- Invocation-scoped mutation responses expose daemon-issued `request_id` in both success and failure paths, alongside typed `error_code` / `message` / `hint` contracts.
- Canonical `agent ... --json` mutation outputs propagate daemon `request_id` for review progression without removing existing script-consumed fields.
- End-to-end S5 coverage includes both happy-path progression and a failure matrix that asserts deterministic outcomes for: not-ready invocation, missing PR, closed PR, mergeability failure, confirmation failure, bounded-input handling, and merge-log persistence failure.
- Failure-matrix assertions validate machine-readable contract stability (typed codes plus `request_id`), not only human-readable stderr text.
- CI wiring runs happy-path and failure-matrix S5 e2e checks as distinct steps so failures are attributable by workflow class.
- CI/operator docs clearly describe how to run the S5 happy-path suite versus the S5 failure-matrix suite locally and in CI.

## Non-Goals

- No new product surface beyond canonical S5 `agent review`, `agent pr sync`, and `agent merge` behavior.
- No merge queue orchestration, GUI/TUI expansion, or policy-driven auto-fix loops.
- No reports-v2 migration or broad CLI ergonomics work (Slice S6 scope).
- No expansion of host/provider scope beyond current GitHub-targeted S5 workflow behavior.

## Key Decisions (if any beyond L2)

**Correlation contract**: `request_id` is the canonical S5 request-correlation field for invocation-scoped mutation/read contracts; `client_request_id` remains an idempotency key for control-plane start/follow-up semantics.

**E2E matrix structure**: treat happy path and failure matrix as separate, first-class contract suites with independent CI visibility.
