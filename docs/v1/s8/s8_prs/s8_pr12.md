# agency — slice 8 / pr-12
## daemon read api + cli read-through-daemon

### purpose

eliminate all cli-side scanning, resolution, reconciliation, and status derivation for v2 flows.

after this pr:
- daemon is the **sole read + derive authority**
- cli is a **pure client + renderer**
- all v2 reads flow through daemon http api
- watch groundwork is unblocked (pr-13)

this pr satisfies **parity rule b**.

---

## scope

### in scope

- daemon **read endpoints** for worktrees and invocations
- daemon-side **ref resolution** (name / id / prefix)
- daemon-side **display status derivation**
- daemon-side **diff + logs read endpoints**
- cli migration:
  - `worktree ls/show/path`
  - `agent ls/show/diff/logs/open`
  - `checkpoint ls`
- unified **response envelope**
- request-id middleware
- minimal pagination support

### explicitly out of scope

- streaming (pr-13)
- watch tui
- repo registry (pr-14)
- mutation endpoints (already implemented)
- performance indexing beyond simple in-memory caching
- `/summary` endpoint — deferred to pr-13 as a caching optimization once event stream provides real data. clients use list endpoints + client-side rollup until then.

---

## architectural invariants

1. **cli never reads v2 store files directly**
   - no `os.ReadDir`
   - no `meta.json` parsing
   - no log file reads
2. **cli never derives status**
   - daemon returns `display_status`
3. **daemon resolves refs**
   - cli passes name / id / prefix verbatim
4. **all daemon responses are versioned + enveloped**
5. **read paths are side-effect free**
   - no reconciliation on read — read endpoints never write meta (already true after pr-11)
   - read endpoints **may consult live signals** (tmux `HasSession`, process map) without writing, to return accurate derived fields between reconciliation ticks
   - daemon background loops (pr-11 reconciler) remain the sole writers for lifecycle state

## daemon api (read)

all responses include the standard envelope:

```json
{
  "ok": true,
  "api_version": 1,
  "build_version": "v0.8.0",
  "git_sha": "abc123",
  "request_id": "uuid",
  "data": { ... }
}

on error:

{
  "ok": false,
  "api_version": 1,
  "request_id": "uuid",
  "error_code": "E_INVOCATION_NOT_FOUND",
  "message": "invocation not found",
  "hint": "use 'agent ls' to list invocations",
  "details": null
}

`details` is an optional structured object. its shape varies by error_code:

| error_code | details shape |
|------------|---------------|
| `E_AMBIGUOUS` | `{ "candidates": ["inv-aaaa", "inv-bbbb"] }` |
| `E_CURSOR_INVALID` | `{ "reason": "filter_changed" }` |
| all others | `null` |

handlers must not add ad-hoc fields outside this envelope. clients may safely ignore `details` if null.

pagination cursor shape

cursors are opaque to clients (`base64(json(...))`), but their internal shape is defined here to prevent incompatible implementations.

| endpoint | cursor fields | tied to ordering |
|----------|--------------|------------------|
| `/invocations` | `{ "started_at": "RFC3339", "invocation_id": "..." }` | started_at desc, invocation_id asc |
| `/worktrees` | `{ "last_used_at": "RFC3339", "worktree_id": "..." }` | last_used_at desc, worktree_id asc |
| `/checkpoints` | `{ "id": 5 }` | id desc |

rules:
- cursor is tied to the current filter + ordering. if a client sends a cursor obtained with different filter/order params, daemon returns `E_CURSOR_INVALID` with `details.reason = "filter_changed"`.
- cursors do not expire but may become invalid after data deletion (return `E_CURSOR_INVALID`).

GET /invocations/{ref}/diff
returns a structured diff with two comparison ranges.

query params
	•	`include_patch` (default 1) — set to 0 to return metadata only
	•	`max_patch_bytes` (default 2097152 / 2mb, max 5242880 / 5mb)
	•	`include_uncommitted` (default 1) — set to 0 to exclude working tree changes

data

{
  "base_commit": "abc",
  "sandbox_branch_tip": "def",
  "has_commits": true,
  "has_uncommitted": true,
  "committed_range": {
    "from": "abc",
    "to": "def",
    "commits": [
      { "sha": "def", "summary": "add tests" }
    ],
    "diffstat": "+42 -15 in 3 files",
    "patch": "diff --git ...",
    "patch_truncated": false,
    "patch_bytes": 14200
  },
  "working_tree": {
    "diffstat": "+8 -2 in 1 file",
    "patch": "diff --git ...",
    "patch_truncated": false,
    "patch_bytes": 4142
  },
  "patch_includes_uncommitted": true
}

rules
	•	`committed_range` covers `base_commit..sandbox_branch_tip` (may be empty if no commits)
	•	`working_tree` covers uncommitted changes vs sandbox branch tip (may be empty)
	•	if sandbox has no commits, `committed_range.commits` is empty and `has_commits` is false
	•	each range has its own `patch` + `patch_truncated` + `patch_bytes`
	•	truncation applies per-range against `max_patch_bytes` (total across both ranges)
	•	read-only git operations only

GET /invocations/{ref}/logs
query params
	•	`kind` — `raw` (stdout log), `stderr`, `stream` (normalized `stream.jsonl`, not live stream — that's pr-13)
	•	`tail_bytes` (default 65536 / 64kb, max 1048576 / 1mb) — byte offset from end of file

data

{
  "kind": "raw",
  "content": "<utf8 text, best-effort decoded>",
  "truncated": true,
  "total_bytes": 1827364,
  "returned_bytes": 65536,
  "starts_midline": true,
  "ends_midline": false
}

framing rules
	•	`content` is byte-sliced from the file, then decoded as utf-8 best-effort (invalid bytes replaced)
	•	`tail_bytes` operates on bytes, not characters
	•	`starts_midline`: true if the returned content begins at a non-zero offset (i.e., the first byte is not the start of a line). clients should discard content before the first newline if rendering lines.
	•	`ends_midline`: true if the file is still being written and the last byte is not a newline
	•	for `kind=stream`: each line in `content` is a complete JSON object (JSONL). partial lines at the start (due to byte slicing) should be discarded by the client.

repo resolution (pre-pr-14)

repo registry is pr-14. until then, the following rule applies:

- if `repo_id` is provided, daemon scopes the query to that repo only.
- if `repo_id` is omitted, daemon **scans all repos** under the data directory (`repo_index.json`). this is acceptable pre-pr-14 given our repo count.
- daemon must not require `repo_id`. cli currently resolves repo from cwd and passes it, but headless callers (watch, scripts) may omit it.

this will be superseded by the repo registry in pr-14.

daemon internals

ref resolution

daemon implements the same algorithm as cli v2 resolvers:
	1.	name match among eligible records
	2.	exact id match
	3.	unique prefix match
	4.	error: not found / ambiguous

cli passes refs unchanged.

⸻

display status derivation

daemon implements:

DeriveDisplayStatus(meta InvocationMeta) (
  display string,
  attentionFlags []string,
  sortKey int
)

precedence
	1.	lifecycle == failed → “failed”
	2.	needs_attention flag → “needs attention”
	3.	semantic == needs_input → “needs input”
	4.	semantic == blocked → “blocked”
	5.	semantic == ready_for_review → “ready for review”
	6.	running + semantic working → “working”
	7.	running → “running”
	8.	finished → “finished”
	9.	starting → “starting”

returned fields:
	•	display_status
	•	attention_flags
	•	sort_key

cli renders verbatim.
