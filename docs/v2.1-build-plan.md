# v2.1 Build Plan

Last updated: 2026-02-05
Status: draft
Source of truth: this doc for build scope and sequencing.

## Direction

v2.1 is an execution-focused release:
- harden and simplify the invocation workflow
- close recovery and review UX gaps
- converge command behavior and automation outputs

## Explicit constraints

1. No GUI in v2.1.
2. TUI work is deferred until v3 at the earliest.
3. Preserve sandbox-first safety invariants.

## Goals

1. Improve agent recovery and workspace access.
2. Add practical chat/review flows that fit current architecture.
3. Make PR/review/merge workflows explicit and machine-readable.
4. Clean up CLI ergonomics (flags, confirmations, shorter commands).
5. Reduce report friction while keeping useful evidence.
6. Move all v2 command reads to daemon read API.
7. Implement runner-portable model with consistent CLI + JSON outputs.
8. Implement restart-from-checkpoint or conversational resume integrated with `agent` commands.

## v2.1 scope

### Committed (high confidence)

1. Daemon API convergence for command reads
- migrate remaining v2 read paths that still scan local store directly to daemon read endpoints.
- target commands include `agent attach`, `agent open`, and related resolution paths.
- acceptance: no v2 read command should require local store scans in CLI command handlers.

2. Agent workspace access suite
- keep `agent open` and add:
- `agent path <invocation>`: print sandbox path only.
- `agent shell <invocation>`: open shell in sandbox path.
- `agent open --editor <name>` parity with worktree command behavior.

3. Recovery and logs
- add `agent logs` with `--follow`.
- add `agent restart <invocation>`:
- headed restart: recreate tmux session against existing sandbox where valid.
- headless restart: explicit restart mode against existing sandbox.

4. Checkpoint-integrated resume
- add checkpoint-aware restart flow in `agent` command family:
- baseline option: `agent restart <invocation> --checkpoint <id>`.
- restore checkpoint, then restart invocation in one guided flow.
- enforce clear safety preconditions and state transitions.

5. Runner portability + output consistency foundation
- replace hard-coded runner allowlists in agent start/control-plane validation with a runner capability model.
- support "raw logs only" fallback for runners without semantic parser adapters.
- add `--json` output to mutation commands in `agent` command family (start/stop/kill/open/restart/pr/review).

6. Review and PR baseline
- add `agent review <invocation>` with:
- summary of status/checks/attention flags
- diff summary and optional patch payload
- `--json` output
- add invocation-centric PR flows (under `agent pr`):
- `create`, `status`, `open`, `merge`

7. CLI ergonomics
- add `--yes` to destructive/confirmation-heavy operations (clean, merge, discard, rm, restart).
- introduce short flags for highest-frequency options where unambiguous.
- add `run --open`.

8. Reports v2 compatibility step
- add optional JSON report artifact (`.agency/report.json`) with minimal schema.
- remove hard requirement for `how to test` in v2 flows.
- keep markdown report compatibility during transition.

### Stretch (medium confidence)

1. Conversational resume (headless)
- first multi-turn continuation path in `agent` commands:
- append follow-up prompt to existing invocation context (or derived continuation context).
- if true continuation is not viable in v2.1 architecture, provide checkpoint-resume fallback and explicit UX.

2. Checks-first watch seed (no full TUI)
- optional minimal terminal view for status/checks only.
- no complex panes; no GUI-style interaction model.

### Deferred (explicitly out of scope for v2.1)

1. Full integrated GUI for chat + review + merge.
2. Full-featured TUI experience (earliest v3).
3. Merge queue orchestration control plane.
4. Policy-aware autonomous AI auto-fix loops from review comments.

## Differentiators to preserve and strengthen

1. Local-first deterministic daemon/state model
- daemon as mutation authority
- predictable local state transitions

2. Runner-portable invocation model
- same command semantics across runners
- capability-driven behavior instead of one-off runner branching

3. Strong checkpoint/rollback tied to sandbox state
- invocation-scoped rollback safety
- restart and resume workflows built on checkpoint semantics

4. Scriptable CLI with consistent JSON
- every key read/mutation path supports automation-grade output

## Sequencing

1. Slice A: daemon-read convergence + `agent path/shell/open --editor`.
2. Slice B: `agent logs --follow` + `agent restart`.
3. Slice C: checkpoint-integrated restart/resume path.
4. Slice D: runner portability foundation + mutation `--json`.
5. Slice E: `agent review` + `agent pr` baseline.
6. Slice F: ergonomics pass (`--yes`, short flags, `run --open`) + reports v2 step.
7. Slice G (stretch): conversational resume and minimal checks view.

## Risks and constraints

1. Daemon API expansion scope
- daemon endpoints will need to cover all read cases currently resolved locally.

2. Restart semantics complexity
- must define exactly when restart reuses sandbox, checkpoints, and conversation context.

3. Runner compatibility debt
- parser/capability behavior must degrade gracefully for new runners.

4. UX migration risk
- old run-centric and new invocation-centric commands can confuse users without clear command hierarchy and docs.
